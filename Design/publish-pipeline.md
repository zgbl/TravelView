# 发布管线设计：从 HEIC 原件到 Facebook 上的一个链接

> 基线：2025 年 9 月横穿美国往返 9300 英里，5354 张照片 / 18.5 GB / 91% 含 GPS。
> 这是我们的第一个真实数据集，所有设计都拿它验证。

---

## 1. 一条铁律：原件不动，只上传衍生图

```
原件 (HEIC/MOV, 18.5 GB)        永远只在用户硬盘上，一个字节都不上传
      |
      | 客户端转换（macOS: ImageIO / AVFoundation，零服务器成本）
      v
分享衍生图 (WebP, 每张 ~200 KB)  只有用户挑中的那些才上传
      |
      v
我们的服务器 = 一个 CDN + 一份 manifest.json
```

这一条同时满足三件事：**服务器没有图像处理负担**（我们连解码器都不需要装）、
**隐私可以被大声宣传**（"你的原图从未离开过这台电脑"）、
**成本可预测**（一次旅行 100 张 × 200 KB = 20 MB，而不是 18.5 GB）。

服务器要做的只有：存 blob、发 URL、渲染页面。它不认识 HEIC，也不需要认识。

---

## 2. 格式选择

### 2.1 你的判断是对的，但有一个例外必须知道

**WebP 就是正确答案**，兼容性早就不是问题了：Chrome / Edge / Firefox / Safari 14+
（2020 年）全部原生支持，覆盖率 97% 以上。同质量下比 JPEG 小 25-35%。

**但是 Facebook 的抓取器不吃 WebP。** 分享链接时用来生成大图预览的 `og:image`
必须是 **JPEG 或 PNG**——喂 WebP 会导致预览图不显示，而预览图恰恰是决定别人点不点的关键。

所以是**两种格式并存**，各司其职：

| 用途 | 格式 | 尺寸 | 目标体积 |
|---|---|---|---|
| 页面里的照片 | **WebP** q80 | 长边 1600 | 150-300 KB |
| 页面里的大图（点开看） | **WebP** q82 | 长边 2560 | 400-700 KB |
| 列表缩略图 | **WebP** q75 | 长边 480 | 30-60 KB |
| 模糊占位（LQIP） | **WebP** q30 | 长边 24 | < 1 KB，内联进 HTML |
| **社交预览 `og:image`** | **JPEG** q85 | **1200 × 630** 裁剪 | < 300 KB |

### 2.2 为什么不用 AVIF

AVIF 比 WebP 再小 20-30%，但 Safari 到 16.4 才支持，更要命的是各家社交平台的
抓取器普遍不认。**收益不值得这个复杂度**，v1 不做。真要做就用 `<picture>`
把 AVIF 作为 WebP 之上的可选优化，让浏览器自己挑。

### 2.3 视频（MOV）

你的库里 MOV 有两种，必须分开对待：

- **Live Photo 的动态部分**：1-3 秒，和同名 HEIC 配对。
  v1 **不上传**，只把配对关系记进库。v2 可以做成"鼠标悬停时轻微动一下"，很讨喜。
- **真正拍的视频**：iPhone 拍的是 **HEVC 编码的 MOV**，浏览器基本不认。
  必须转成 **H.264 + AAC 的 MP4**（AVFoundation 在客户端转，同样零服务器成本）。
  v1 先只取首帧当封面图，视频本身排到 v2。

## 3. 一次旅行的数据形态

9300 英里的横穿显然不能是"一篇游记"。数据模型分三层：

```
Trip     2025 横穿美国往返            总览：全程地图 + 数据总结
 └─ Segment  01 加州 -> 大峡谷        一个可以单独分享的页面
     └─ Node    羚羊谷                一个地点，若干张照片
```

`segment` 就是 `tag` 表里的一种 kind，不需要改架构。

**分段策略**（自动生成、用户可改）：
1. 优先按"住宿点"切分——夜间长时间静止的位置就是一天的终点
2. 单段超过 6 天或 800 英里就再切
3. 每段自动起名："Day 3-5 · 大峡谷 - 纪念碑谷"

这样你可以**分段发布、分段测试**，正好对应你说的做法。

## 4. 分享页面的形态

### 4.1 URL

```
https://<域名>/t/<slug>              整个旅行的总览
https://<域名>/t/<slug>/s/<segment>  某一段
```

slug 用不可猜测的随机串（如 `9f3a2b`），这样"仅链接可见"是真的私密——
没有链接的人猜不到。用户可以选择公开、密码保护、或设置过期。

### 4.2 页面结构

1. **封面**：一张大图 + 标题 + "2025年9月 · 21天 · 9300英里 · 12个州"
2. **全程地图**：路线逐段绘出，节点按顺序点亮（这是横穿美国的杀手锏，
   一条横贯大陆的线本身就极有冲击力）
3. **按段落展开**：每段一个小标题 + 地图高亮 + 照片流
4. **数据总结卡片**：天数、里程、州数、照片数、最高海拔、走过的国家公园
   —— **专门为被截图转发而设计**，这是传播的引爆点

### 4.3 Facebook 分享要点

页面 `<head>` 必须有：

```html
<meta property="og:title"       content="横穿美国 9300 英里">
<meta property="og:description" content="2025年9月 · 21天 · 12个州 · 340张照片">
<meta property="og:image"       content="https://.../cover-1200x630.jpg">
<meta property="og:image:width"  content="1200">
<meta property="og:image:height" content="630">
<meta property="og:url"         content="https://.../t/9f3a2b">
<meta property="og:type"        content="article">
<meta name="twitter:card"       content="summary_large_image">
```

三个容易踩的坑：

1. **`og:image` 必须是 JPEG/PNG 的绝对 URL**，且要能被匿名访问
   （Facebook 的爬虫没有登录态）。私密链接的封面图因此不能鉴权。
2. **Facebook 会缓存抓取结果**。改了标题或封面后，要去
   Sharing Debugger 手动 Scrape Again，否则永远显示旧的。
3. **必须服务端直出这些标签**。爬虫不执行 JavaScript，
   纯前端 SPA 渲染的 og 标签它读不到 —— 这直接决定了分享站要用
   SSR 或静态生成，不能用纯客户端渲染。

## 5. 客户端导出管线（要写的代码）

```
选中的照片
  -> ImageIO 解码 HEIC（已有 makeThumbnail 的基础设施）
  -> 按 EXIF Orientation 摆正
  -> 缩放到各档尺寸
  -> 剥离全部 EXIF（GPS 绝不进衍生图；位置只以"节点"粒度出现在页面上）
  -> 编码 WebP（封面另出一份 JPEG）
  -> 写入 <库>/views/by-trip/<trip>/web/
  -> 生成 manifest.json
  -> 上传（只传这个目录）
```

**注意**：macOS 的 ImageIO 从 Big Sur 起支持写 WebP，直接
`CGImageDestinationCreateWithURL(..., "org.webmproject.webp", ...)` 即可，
不需要引入任何第三方库。Windows 侧要用 WIC 或带一个 libwebp，届时再说。

导出目录同时写进本地库，所以**用户在自己硬盘上也有一份可离线浏览的成品**——
这就是之前说的"插上硬盘双击 index.html 就能看"，和上传的是同一份产物。

## 6. 下一步做什么（按顺序）

当前 App 能导入、能建库、能校验，但**还看不出一次旅行长什么样**。
下面五步走完，就能把你这次横穿发出去：

| 步 | 内容 | 为什么是这个顺序 |
|---|---|---|
| **A** | **HEIC/MOV 缩略图**（已完成，待你验证） | 看不见照片，后面每一步都没法做判断 |
| **B** | **Live Photo 与编辑版配对** | 你的库里 `IMG_1431` 和 `IMG_E1431` 是同一张照片的原片和编辑版，现在被当成两张。不合并，挑图时会重复、数量也不准 |
| **C** | **停留点聚类 + 地图**（已完成 MVP，待验证） | 第一次看到 9300 英里的形状。这是整个产品的"魔法时刻"，也是最该早点看到的东西 |
| **D** | **分段 + 挑图 UI** | 把 5354 张收敛到可发布的几百张 |
| **E** | **导出管线 + 分享页** | 拿到那个能发 Facebook 的链接 |

**B 值得单独说**：Apple 的 `IMG_E1431` 里的 `E` 就是 edited。我们的
`PhotoRecord.edit_of` 字段已经预留好了，但导入时还没有填。规则是
"文件名去掉 `E` 前缀后能在同一天找到对应原片，就建立关联"，
UI 上折叠成一张，默认用编辑后的版本（那是用户自己调过的，更好看）。
Live Photo 同理：同名的 HEIC + MOV 配成一对。

**C 之前需要补一件事**：你这次横穿了多个时区，而 EXIF 的 `DateTimeOriginal`
是**不带时区的本地时间**。好消息是这恰好是我们想要的——用户体验到的就是当地时间，
按它分日是对的。但要额外记下 `OffsetTimeOriginal`，否则跨时区计算行程时长会出错。

## 7. 地图 MVP 的算法说明（已实现，`tv_core/lib/src/route.dart`）

### 7.1 为什么不用经典的停留点检测

教科书上的停留点检测（滑动窗口 + 半径/时长双阈值）假设输入是**均匀采样的 GPS 轨迹**。
而我们的输入是照片——**稀疏且极不均匀**：一个景点可能连拍 30 张，
然后开车四小时一张都没有。用滑动窗口会把"开车四小时"误判成一次长停留。

所以改用**增量聚类**：按时间顺序走，遇到下面任一情况就开一个新节点。

1. 离当前簇中心超过半径（默认长途 1500 米 / 城市 300 米）
2. 距上一张照片的时间间隔超过阈值（长途 2 小时 / 城市 45 分钟）

第 2 条很关键：在同一个营地待了一夜，早上和晚上应该算**两次**停留，
不然"Day 3"和"Day 4"会被粘成一个节点。

### 7.2 碎片合并

长途自驾会在路上随手拍单张照片，每张都会变成一个孤立节点，
把 9300 英里的路线打成一地碎片。所以长途预设要求每个节点至少 2 张照片，
不够的**并进时间上更近的邻居**，而不是丢弃——测试里专门断言了"合并不能丢照片"。

### 7.3 交通方式

由两点间平均速度反推: > 300 km/h 判为飞行，> 12 km/h 判为自驾，其余为步行。
飞行段在地图上画紫色虚线，自驾画实线——横穿美国的往返如果中间有段飞行，
一眼就能看出来。

### 7.4 已知的简化（v1 可接受）

- **路线是节点间的直线**，不是实际道路。要贴合真实公路需要接路径规划服务，
  是联网且收费的操作，与"零服务器成本"的原则冲突。直线在洲际尺度上视觉效果
  其实很好，城市尺度才会显得假。
- **地名还没有**，节点目前显示经纬度。反查地名是下一步。
- **时区**：EXIF 的时间是不带时区的本地时间，跨时区时"停留时长"会有偏差。
  按当地时间分日是对的（那是用户体验到的），但算总时长需要 `OffsetTimeOriginal`。
