# TravelView 照片备份功能规划

## 0. 先说三句实话

**这个方向是对的。** 备份和游记不是两个功能，是同一件事的两面：游记是**获客**（做完想炫耀，链接传出去带新用户），备份是**留存**（一年打开 12 次，而不是 2 次）。而且 App 已经拿到了相册权限、已经扫过全库元数据——增量成本比从零做一个备份 App 低得多。

**但它不是"顺便"。** 这是第二个产品，工作量和游记功能相当，甚至更大。原因见下一节：iOS 上手机没法直接写你电脑的硬盘，你需要**再做一个桌面端**（好消息：你有 Tauri 经验）。建议把它排在游记 MVP 跑通之后，作为 V1.5，而不是塞进第一版。

**定位上给个建议**：别在产品文案里攻击 Apple。用户对 iCloud 的不满是真的，但"苹果很坏"这种表达会招来一批杠精，也容易踩 App Store 审核的模糊地带。正面表达更强：**"你的照片，存在你自己的硬盘上"**。同类 App（PhotoSync、iMazing）都是这个调性，活得好好的。

---

## 1. 硬约束：必须先想清楚的技术现实

### 1.1 iOS 不能直接写你的电脑

iPhone App 没有任何办法把文件写进 Mac 的文件夹。可行的只有三条路：

| 路径 | 做法 | 评价 |
|---|---|---|
| **A. 手机推、电脑收** | 手机通过 mDNS/Bonjour 发现同网段的桌面端，HTTP 推送 | **推荐**。手机知道哪些是新的，逻辑最自然；桌面端就是你的 devsink 长大版 |
| B. 电脑拉、手机当服务器 | 手机起个 HTTP/WebDAV 服务，桌面端来拉 | 手机后台一挂服务就断，体验差 |
| C. 手机直连移动硬盘 | iOS 13+ 通过 UIDocumentPicker 拿到 U 盘/SSD 的安全书签，直接写 | **完全不用电脑**，是个亮点。但 iPhone 12 是 Lightning 口，要转接头且供电吃紧；iPhone 15+ 的 USB-C 就很爽 |

**结论**：A 为主（需要 Tauri 桌面端），C 作为无电脑用户的备选。

### 1.2 iOS 后台会被杀

系统不允许 App 长时间后台跑传输。现实做法：**插电 + 连 Wi-Fi + 保持 App 前台**，配合"保持屏幕常亮"。一次旅行几百张，十几分钟的事，用户能接受。别承诺"自动后台备份"，做不到，承诺了就是差评。

Android 相反：`WorkManager` + 前台服务可以真后台跑，还能直接写 OTG 移动硬盘和 SD 卡（SAF tree URI）。**Android 版本的备份体验会明显好于 iOS**，这个要认。

### 1.3 iCloud「优化存储」是最大的坑

开了优化存储的用户，手机上只有缩略图，原图在 iCloud 上。备份时必须先把原图拉回来：
```
PHImageRequestOptions.isNetworkAccessAllowed = true
```
后果是：第一次全量备份可能要下载几十 GB、耗时几小时、走用户流量。

**这必须在 UI 上提前讲清楚**："检测到 3,412 张照片的原图不在本机，需要先从 iCloud 下载约 47 GB。建议连 Wi-Fi 并插电。" 不讲清楚，用户会以为你的 App 卡死了。

### 1.4 什么才算"完整备份"

只存一张 JPG 不叫备份。真正要处理的：

- **Live Photo** = HEIC + MOV 一对，丢了 MOV 就丢了实况
- **编辑过的照片** = 原片 + 编辑后版本，两个都该留（至少留编辑后的）
- **RAW+JPEG 对**、连拍组、人像模式的景深数据
- **相册结构、收藏、标题** 只存在 Photos 数据库里，文件系统里没有——必须导出 sidecar（JSON 或 XMP），否则用户换个电脑就什么都没了
- 文件的**修改时间要设成拍摄时间**，否则在 Finder 里排序全乱

这一堆细节，正是市面上免费工具做得烂、而用户愿意为之付费的地方。

## 2. 你独有的差异化：按「旅行」分文件夹

所有备份工具都只会按日期建文件夹。**而你的 App 已经算出了行程和地点**——这是别人抄不走的。

```
Photos/
  2025/
    2025-03-14/                          日常照片，按日期
    2025-09-12 京都·大阪 8天/            ← 只有你能生成这个
      01 伏见稻荷/
      02 清水寺/
      03 岚山/
      trip.json                          行程元数据
      index.html                         离线可看的游记（插硬盘就能浏览）
  _sidecar/
    albums.json                          相册结构、收藏、标题
```

**`index.html` 这一步是点睛之笔**：把生成好的游记页面一份写进硬盘。十年后把硬盘插进任何一台电脑，双击就能看到带地图和时间线的旅行回顾，不依赖你的服务器、不依赖网络、不依赖你公司还在不在。这句话本身就是最好的宣传语。

目录模板做成可选（纯日期 / 日期+地点 / 按旅行分组），默认给最聪明的那个。

## 3. 功能推荐

### 3.1 必须有（否则不算备份工具）

- **增量、幂等、可断点续传**。本地一份 catalog（assetId + 内容哈希 + 目标路径 + 状态），跑一半断电，下次接着跑。
- **只读手机、永不删除**。这条要写进 UI 里做成明确承诺，和游记功能的隐私承诺是同一套话术。
- **校验（verify）**。备份完在目标端重新算哈希比对。没有校验的备份是自我安慰。做成一个可单独运行的"体检"按钮。
- **多目的地**：Mac + 移动硬盘 + NAS(SMB)，各自独立记录进度。3-2-1 备份原则本来就要求多份。
- **覆盖率仪表盘**：首屏直接给一个数字——"你有 3,412 张照片（47 GB）从未备份到任何地方"。这个数字是整个功能的转化钩子，比任何文案都有说服力。

### 3.2 用户会真心喜欢的

- **最旧优先**：默认从最老的照片开始备份，而不是最新的。用户跑一半退出去了，救回来的也是最珍贵、最容易永久丢失的那批。这个细节几乎没人做。
- **离线硬盘提醒**："你的移动硬盘上次插入是 47 天前，期间新增 312 张照片。" 备份工具的真正敌人是遗忘，不是带宽。
- **安全清理助手**：只对"已在两个目的地校验通过"的照片，提示可释放多少空间。**但绝不代替用户删除**，只是把它们筛进一个相册，让用户自己在系统相册里删。既有价值又不担责任。
- **重复照片 / 连拍择优**：同一秒连拍 9 张，只备份最清晰的那张（其余可选）。省空间又省用户的整理时间。
- **兼容副本**：保留 HEIC 原件的同时，可选同步导出一份 JPEG。给"想用旧电脑或旧软件打开"的用户，这个需求比你想象的大。
- **年度回顾 / 这一天**：备份数据本来就在手边，顺手做"三年前的今天"。零额外成本，纯留存收益。

### 3.3 想清楚再做

- **自动后台备份**：Android 能做，iOS 做不到。别做成跨平台承诺。
- **加密备份**：听起来专业，但会让"插硬盘直接看照片"这个最大优点失效。若要做，做成可选，且默认关。
- **备份到你自己的云**：那就变成和 iCloud 同一个生意，也是同一种被讨厌。不建议。

---

## 4. 架构上的增量

游记功能的架构基本不动，新增两块：

- **桌面端（Tauri）**：Bonjour 广播、接收 HTTP 推送、写文件系统、校验、管理多个目的地。你有 Tauri 经验，这块是你的舒适区。
- **App 内备份引擎**：catalog（SQLite，和扫描缓存共用）、任务队列、断点续传、哈希计算。

两端之间**不经过你的服务器**，纯局域网。这既是隐私卖点，也意味着这个功能的边际成本是零——用户越多你也不多花一分钱。这一点和游记功能的图片存储成本形成对冲，商业模型上很健康。

---

## 5. 商业上的一句话

游记功能免费（要靠它传播），备份功能是**一次性买断或订阅**的自然候选：它持续提供价值、有明确的替代品价格锚（iCloud 每月订阅），而且用户为"不丢照片"付费的意愿远高于为"做个网页"付费。

---

## 6. 建议的顺序

1. 游记 MVP 跑通、自己发一篇出去（先验证核心价值）
2. Android 版备份（技术上最顺，能直写 OTG 硬盘，先跑通全套逻辑）
3. Tauri 桌面端 + Bonjour 推送
4. iOS 备份（处理 iCloud 下载、Live Photo、前台限制这些脏活）
5. 覆盖率仪表盘、校验、清理助手这些"讨人喜欢"的层

第 2 步就能拿你的 OPPO 真机验证完整链路，不用等桌面端。
