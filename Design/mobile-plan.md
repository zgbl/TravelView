# 手机端方案

最后更新：2026-09-09

桌面端告一段落，开始做手机端。这份文档记的是**为什么这么分**，
不是怎么写代码 —— 代码会变，这些取舍不会。

## 一、不新建 mobile 目录

`apps/tv_app/` 从一开始就是给手机端留的位置，直接在那儿做。
Flutter 一套 Dart 代码同时出 iOS 和 Android，需要分开处理的只有三处：

- 相册权限（Android 13+ 的 `READ_MEDIA_IMAGES` vs iOS 的 `NSPhotoLibraryUsageDescription`）
- 系统分享面板（`share_plus` 封装掉）
- 打包与签名

## 二、手机端不建照片库

**这是整个手机端最重要的一个决定。**

桌面端的照片库是"把照片按内容哈希收进一个目录"。手机端**不这么做**：
手机里已经有一份完整的相册，再在 App 沙盒里存第二份，等于凭空吃掉
几十 GB，还要处理两份之间的同步。

所以手机端只做**读者**：

- 通过 `photo_manager` 读系统相册的元数据（时间、GPS、宽高）
- 转成 `tv_core` 认识的 `PhotoRecord`，精选 / 聚类 / 成篇算法一行不改
- 发布时才导出选中的那几十张派生图上传

代价是 `PhotoRecord.id` 在手机上不是内容哈希，而是系统给的资产 id
（iOS 的 localIdentifier / Android 的 MediaStore id）。这个 id
**只在这台手机上有意义**，所以它不写进 sidecar、不参与库的自愈；
服务器那边用派生图自己的哈希做身份。

手机端因此**不是照片库的第二个副本**，而是它的一个视图。
备份仍然只有桌面端做。

## 二·五、手机上的临时工作目录

"不建照片库"**不等于"不写文件"**。发布一篇 Story 要先把选中的照片缩小、
剥掉元数据、打成一个包，这些中间产物必须有地方放。

`Workspace`（`apps/tv_app/lib/state/workspace.dart`）是手机上唯一会被写入的地方，
三条铁律：

1. **绝不碰系统相册里的原件。** 要缩放、要剥元数据，都在这里做副本。
2. **里面的东西全都可以随时删掉重建。** 丢了顶多重做一遍，不丢用户任何数据。
3. **不依赖任何外部设备。** 真实用户手上只有一部手机，发布直接从这里上传。

目录放在**系统的缓存目录**（iOS 的 Caches / Android 的 cacheDir），不是 Documents：

- 不会被备份进 iCloud —— 几百 MB 的派生图备份上去毫无意义
- 手机空间紧张时系统可以自己清掉

代价是**随时可能被清空**，所以每次用之前都要检查文件还在不在，
不能把它当持久存储。草稿、设置这些要留住的东西存在 `AppSettings` 那边。

里面分三类：`export/<storyKey>/` 待上传的派生图、`bundle/<storyKey>/` 打包产物、
`analysis/` 精选算法用的小图。**发布完就删**，不留着"万一还要用" ——
派生图随时能重新生成，攒着不删会在用户手机上悄悄堆出几个 GB。
另外每次启动扫一遍，删掉三天没动过的：用户在发布中途杀掉 App 很常见，
那一次的产物就永远没人删了。

`MobileImageOps` 里还有一道护栏：写入路径不在 `Workspace` 里就直接拒绝，
免得哪天某段共享代码按桌面端的习惯把文件写到别处去。

## 二·六、USB 和 devsink 只属于开发期

`Design/dev-setup.md` 里的 USB 连线、`adb reverse`、`tools/devsink`
**全部只是开发期用来看日志和产物的**。真实用户手上只有一部手机，
不会连着线。

因此：

- App 的任何功能都不能以"连着电脑"为前提
- devsink 的地址走 `--dart-define=DEVSINK=...`，**不填就整个功能不存在**，
  release 包里不该有任何指向局域网地址的代码路径
- 手机端不需要桌面端在场也能完成"看 → 生成 → 分享"的完整闭环

手机和桌面之间**没有运行时依赖**，只有一份共享的 Story 契约。

## 三、三层怎么分

判断一段代码放哪，标准只有一条：**手机端和桌面端是不是同一份逻辑。**

| 层 | 内容 | 依赖 |
|---|---|---|
| `packages/tv_core` | 纯算法：哈希、sidecar、catalog、聚类、成篇、路线 | 纯 Dart |
| `packages/tv_shared` | 两端同一份、但要用 Flutter 或 dart:io：界面语言、设置、草稿、Story 导出 | Flutter |
| `apps/tv_desktop` | 多窗口、快捷键、鼠标、MTP 读手机 | macOS |
| `apps/tv_app` | 触摸界面、系统相册 | iOS / Android |

`tv_shared` 是这次新加的一层。原来这些代码都在 `tv_desktop/lib/state`
和 `lib/export` 里，其实和桌面没有任何关系。

## 四、平台差异只有一个接口

共享层碰得到的平台差异全部收在 `ImageOps` 一个抽象类里：读元数据、
出缩略图、出网页派生图、算精选信号、旋转。

- 桌面端：`DesktopImageOps` 转发给 macOS 的 ImageIO（原有的 `NativeBridge`）
- 手机端：`MobileImageOps` 走系统相册的解码器
- 没接原生层的平台（比如 Windows）：默认的 `NoImageOps` 全部安全降级

App 在 `main()` 里 `ImageOps.register(...)` 一次，共享代码里
一个 `MethodChannel` 都不会出现。

配置目录同理：手机上沙盒路径要问系统要，所以 `AppSettings.configDir`
留了个注入点，桌面端不设，走原来按平台拼的默认值。

## 五、手机端做什么，不做什么

**手机端必须能独立走完全程：看 → 挑 → 生成 → 分享。**

一开始我把"挑图"划给了桌面端，这是错的。手机用户不可能为了发一篇回顾
去开电脑 —— 那样这个 App 就没有存在的理由了。**凡是"发出去"这条链路上的
步骤，手机端一个都不能少。**

1. 打开就看见"你去过的地方"，一趟一张卡片
2. 进去是照片和地图两个 tab
3. 一键生成回顾，调系统分享面板发出去

**留在桌面端的只有"精修"**：旋转裁剪、Stop 手工编排、AI 文案调参、
几百张照片的批量整理。这些在手机上做是折磨，而且**不做也能把东西发出去** ——
这才是判断标准：少了它用户还能不能完成发布。少了就必须做在手机上。

手机端也**不改动系统相册里的原件**。这不是保守，是边界：
App 没有理由去写用户的原始照片。

## 五·五、挑图是减法，不是加法

默认全选（截图除外），用户把看着不顺眼的划掉。

**不是默认全不选让用户一张张勾。** 用户点进一趟行程，想的是"把这次旅行发出去"，
不是"从三百张里挑三十张"。默认空的话，他要先干三分钟体力活才能看到第一个结果，
而这三分钟里他还不知道结果长什么样，凭什么判断该留哪张？

**所有挑图操作都在屏幕下半部。** 竖握手机时拇指扫得到的只有底下三分之一，
把勾选和批量操作放进顶部的 AppBar，等于每点一次都要换手或者挪握姿 ——
挑三百张照片的过程中要挪三百次。顶部只放数字（"已选 47 / 312"），
数字是用来看的，按钮是用来点的，只有前者适合放在够不着的地方。

看大图时的"要 / 不要"做成**横贯屏幕宽度、贴着底边的一整条**：
拇指随便往下一按就中，不用瞄。

三个入口，对应三种真实的想法：

- **按天批量** —— "第三天全是在车上拍的，不要了"。手机上让用户点掉四十张是折磨
- **网格里点** —— 明显重复的连拍，缩略图上就能判断
- **看大图时勾** —— 哪张更清楚、谁闭眼了，非放大不可。挑图真正发生在这里

地图 tab 画的是**选中照片**的路线，挑完回来看一眼就知道这一篇会走出什么形状。

等阶段 2 接上 `Curator`，默认值从"全部"换成"自动精选出来的那批"，
**交互一个字都不用改** —— 用户照样是在一个已经成形的结果上做增删。

## 五·七、发布：手机独立完成，桌面不在链路上

`tv_core` 里的 `Publisher` 是纯 Dart，断点续传、额度、原地更新全都有，
手机上直接能跑。真正要解耦的只有一处：`StoryExporter` 原来绑死在
`Catalog` + `libraryRoot` 上，而手机端没有照片库。

抽出 `StorySource`，只有两个方法：

- `byId(id)` -> 照片记录
- `sourceOf(id)` -> **原样交给 `ImageOps.exportWeb` 的那个字符串**

桌面端的 `CatalogSource` 返回绝对文件路径，手机端的 `AlbumSource`
返回系统相册的资产 id。导出逻辑（挑哪些、缩多大、写什么 manifest）
两端一模一样，不需要知道自己拿到的是哪一种。

产物目录也从写死的 `views/by-trip/` 变成调用方传的 `outRoot`：
桌面端仍然写进照片库，手机端写进 `Workspace`，**发布成功就删**。

登录复用桌面端那个 `/api/desktop/login` —— 一个账号在哪台设备上登录都一样，
没有理由为手机再造一套。注册、找回密码、改资料全在网页上，App 不做。

进度分两段报：导出是本地算力，上传是网络。用户卡在哪一步、该不该换个
Wi-Fi，只有分开报才看得出来。上传中断时服务器给的 `storyId` 必须留住，
重试才是接着传那一篇，而不是又建一篇、又扣一次额度。

## 六、行程是怎么切出来的

连续两张照片之间隔了超过 20 小时就算两趟；切完之后只留下
"看起来真的是出门了"的段落 —— 够多张（8 张以上），并且
够多天（2 天以上）或者跑得够远（跨度 25 公里以上）。

三个条件里满足一个就行，因为一日游、一周宅家拍娃、一次跨国飞行
是三种完全不同的形状。

**猜错了不要紧**：界面上永远保留"自己选时间范围"这条路。
自动只是省事，不是唯一入口 —— 把自动当成唯一入口，
用户第一次被切错就再也不信它了。

## 七、分阶段

- **阶段 0**（已完成）抽出 `tv_shared`，桌面端改成依赖它，行为零变化
- **阶段 1**（进行中）手机端脚手架：相册权限、行程识别、时间轴、地图
- **阶段 2** 自动精选 + 成篇预览（接 `Curator` 和 `StoryBuilder`）
- **阶段 3** 发布、分享、双平台打包

阶段 1 里 `MobileImageOps.analyze` 还没实现（清晰度 / 人脸 / 感知哈希），
`Curator` 会退回到"只按时间和位置聚类"，精选质量差一些但不会崩。
阶段 2 再补。
