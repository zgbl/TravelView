# TravelView 架构与产品规划 v0.1

> 定位：**手机 App 为核心**。用户旅行回来，App 在本地扫描相册 → 自动还原路线与行程节点 → 用户挑图 → 一键生成可分享的旅行回顾网页（视频为后续版本）。
> 隐私模型：**端侧解析，选中才上传**。EXIF/GPS 永不离开手机，只有用户明确挑选的照片会被压缩后上传。

---

## 1. 核心用户流程（四步）

```
① 选范围            ② 自动生成行程          ③ 逐节点挑图           ④ 发布分享
日期区间 / 目的地  →  地图路线 + 时间轴节点  →  节点内缩略图多选  →  生成网页链接 + 二维码
   (5 秒)              (本地计算, 3-10 秒)       (真正花时间的一步)      (上传 + 发布)
```

设计上唯一需要用户"动脑"的是第 ③ 步，其余全部自动。第 ② 步必须做到"打开就有结果"，这是产品的魔法时刻。

**降低门槛的关键决策**：第 ①②③ 步全程不需要注册。只有第 ④ 步发布时才要求登录（或用匿名设备 ID 先发布、后续绑定账号）。

## 2. 关键技术难点（这个项目真正的护城河）

### 2.1 拿到照片的 GPS —— 平台差异是第一个坑

| 平台 | 机制 | 坑 |
|---|---|---|
| iOS | PhotoKit `PHAsset.location` / `.creationDate` | 需要 **完全访问** 相册权限；"仅选择部分照片"模式下拿不到全库时间线。必须做权限引导 UI |
| Android | MediaStore | **Android 10+ 默认抹掉位置**。必须申请 `ACCESS_MEDIA_LOCATION` 并对 URI 调 `setRequireOriginal()` 才能读到 GPS |
| 通用 | — | 部分照片无 GPS（截图、微信保存图、关了定位）；需要按**时间插值**从相邻有 GPS 的照片推断位置 |

> Flutter 侧用 `photo_manager` 可拿到 `AssetEntity.latitude/longitude/createDateTime`，但 Android 的 `ACCESS_MEDIA_LOCATION` + `setRequireOriginal` 大概率要写一小段 **Platform Channel 原生代码**兜底。这是必须先做的技术验证。

### 2.2 扫描性能
一次旅行可能几百张，整个相册可能几万张。策略：
- 只按 `createDateTime` 范围查询，**不解码图片**，只读元数据（`photo_manager` 的 filter 直接在原生层过滤）。
- 缩略图按需懒加载 + LRU 缓存，节点展开时才取。
- 扫描结果落 SQLite，二次进入秒开。

### 2.3 从 GPS 点串还原"行程节点"（核心算法）

不是简单画折线，而是要识别**停留点（Stay Point）**：

```
输入: [(lat, lon, time)] 按时间排序
1. 停留点检测: 滑动窗口，若连续照片在半径 R 内且跨度 > T，合并为一个"节点"
   经验值: 城市内 R=300m / T=20min；跨城 R=2km
2. 节点间为"移动段"，按时间跨度 + 直线距离推断交通方式（步行/驾车/飞行）
   > 500 km/h ⇒ 飞行，画大圆弧虚线；否则画实线
3. 按自然日切分为"Day 1 / Day 2 ..."
4. 每个节点取照片数最多、清晰度最好的一张作为封面候选
```

### 2.4 地名反查（Reverse Geocoding）
节点要有名字（"清水寺"而不是"34.99, 135.78"）。方案：
- **端侧兜底（零成本）**：内置 GeoNames `cities15000` 数据集（~2MB），离线给出城市级名称，保证断网可用。
- **精确名称**：调用一次反查 API 拿 POI 级名称。国内覆盖用高德/腾讯，国外用 Mapbox 或 Nominatim。**由后端代理调用**，不把 key 放进 App。
- 每个节点只查 1 次（用中心点），几百张照片也就十几次请求，成本可忽略。

### 2.5 坐标系（中国项目必踩）
EXIF 里是 **WGS-84**，高德/腾讯地图瓦片是 **GCJ-02**，百度是 BD-09。境内点位直接画会偏移 300~500m。
- 决策：**内部一律存 WGS-84**，只在渲染到国内地图时做 GCJ-02 转换。
- 分享网页若用 MapLibre + OSM/Mapbox 瓦片，则不需要转换（境内地图合规性需另行确认）。

### 2.6 图片处理管线
iPhone 拍的是 **HEIC**，浏览器兼容性差且体积大。
- 端侧：`AssetEntity.file`（iOS 自动转码 JPEG）→ 等比缩放长边 2048 → 编码 WebP（q=82）→ 通常 200-400KB。
- **主动剥离 EXIF**（含 GPS）后再上传，位置信息只以节点粒度出现在网页上，用户可选择"隐藏精确坐标"。
- 上传走 **预签名 URL 直传对象存储**，不经过业务服务器。

## 3. 系统架构

```
┌──────────────────────── 手机 App (Flutter) ────────────────────────────────┐
│  相册层        photo_manager → EXIF/GPS/时间（原生 Channel 兜底）         │
│  行程引擎      停留点聚类 · 分日 · 交通方式推断 · 封面挑选（纯 Dart）   │
│  本地存储      SQLite(drift) 存扫描结果与草稿 · 缩略图 LRU 缓存           │
│  编辑 UI       地图 + 时间轴 + 节点挑图 + 文案编辑                         │
│  上传          压缩/转码/去 EXIF → 预签名 URL 直传                        │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ REST/JSON (仅元数据，KB 级)
┌───────────────────────────────▼───────────────────────────────────────────┐
│  API 服务       鉴权 · 游记 CRUD · 预签名签发 · 地名反查代理 · 发布    │
│  对象存储       原图(WebP) + 多档缩略图，CDN 回源                          │
│  数据库         用户 / 游记 / 节点 / 照片 / 分享统计                       │
│  分享站         travelview.xx/t/{slug} — 读 manifest.json 渲染            │
└────────────────────────────────────────────────────────────────────────────┘
```

**发布产物的关键设计**：一篇游记 = 一份 `manifest.json`（节点、坐标、时间、文案、图片 URL）+ 一个**通用渲染前端**。不为每篇游记生成一份 HTML，这样以后升级模板，所有老游记自动获得新样式。manifest 走 CDN，分享页几乎零后端成本。

## 4. 技术栈推荐

### 移动端（已定 Flutter）

| 用途 | 选型 | 说明 |
|---|---|---|
| 相册访问 | `photo_manager` | 事实标准，支持批量元数据查询 |
| 权限 | `permission_handler` + 原生 Channel | Android `ACCESS_MEDIA_LOCATION` 要自己补 |
| 地图 | `flutter_map` (+ MapLibre 瓦片) | 免费、可换源；`mapbox_maps_flutter` 效果更好但收费 |
| 本地库 | `drift` (SQLite) | 类型安全，迁移友好 |
| 状态管理 | `riverpod` | — |
| 图片处理 | `flutter_image_compress` | 支持 HEIC→WebP |
| 上传 | `dio` + 分片/断点续传 | 弱网是真实场景 |
| 地理计算 | 自己写（Haversine + 聚类） | 逻辑不复杂，别引重库 |

### 后端方案对比（你要的对比，最终由你定）

| 方案 | 起步速度 | 成本 | 优点 | 风险 |
|---|---|---|---|---|
| **A. Go + Cloudflare R2 + Postgres**（推荐） | 中 | 极低（R2 零出网费） | 你最熟；图片流量是这个产品的大头，R2 免出网费直接决定单位经济模型；完全可控 | 鉴权、预签名、分享站要自己写（约 1-2 周） |
| **B. Supabase** | 最快 | 免费档够 MVP，涨量后偏贵 | Auth + Storage + Postgres + RLS 开箱即用，一周能跑通全链路 | Storage 出网费；后期迁移有成本；RLS 心智负担 |
| **C. Firebase** | 快 | 中 | 移动端 SDK 生态最好 | 国内访问不稳定，对你的用户群是硬伤 |
| **D. 纯端侧导出静态包** | — | 零 | 无服务器 | 没有在线链接，等于放弃"分享炫耀"这个核心价值 |

**建议**：MVP 阶段 **B 起步验证产品**，或直接 **A**（若你不介意多花一两周）。考虑到 ①你 Go 很熟 ②图片型产品对存储出网费极度敏感 ③国内访问，我倾向 **A**：Go(Gin/Echo) + Postgres + Cloudflare R2 + CDN，分享站用 Vue3/Vite 或 Astro 静态化。

### 分享网页
- **MapLibre GL JS** 画路线（矢量瓦片，可自托管 Protomaps 彻底去依赖）
- 滚动驱动的地图动画（scrollytelling）：页面滚到 Day 2，地图自动飞到 Day 2 节点
- Astro / Vue3 + SSG，首屏 HTML 直出，SEO + 秒开
- 图片 `<picture>` + AVIF/WebP 多档 + 懒加载 + LQIP 模糊占位

            slug, visibility(private/link/public), theme, published_at
node        id, trip_id, seq, day_index, name, lat, lon,
            arrive_at, leave_at, note, transport_to_next

            blurhash, is_cover, caption

## 6. 功能规划

### MVP（目标：自己用 iPhone 12 Pro Max 的真实旅行照片跑通）
- [ ] 相册权限引导（iOS 完全访问 / Android ACCESS_MEDIA_LOCATION）
- [ ] 按日期范围扫描，展示"发现 N 张照片，跨越 M 个地点"
- [ ] 停留点聚类 → 地图路线 + 时间轴节点列表
- [ ] 节点详情：该节点照片网格，多选（默认智能预选 6-9 张）
- [ ] 节点改名 / 合并 / 删除 / 手动新增
- [ ] 一键生成 → 上传 → 得到分享链接 + 二维码
- [ ] 分享网页：封面 + 地图路线 + 按天时间轴 + 照片流

### V1
- [ ] 目的地反向筛选（输入"京都"自动圈出对应照片）
- [ ] AI 自动文案：给节点和整篇游记起标题、写一句话说明
- [ ] 多套视觉主题（杂志风 / 极简 / 胶片）
- [ ] 统计数据条：行程天数、总里程、去过几个城市、拍了多少张
- [ ] 草稿云同步、多设备编辑
- [ ] 隐私控制：模糊家附近坐标、隐藏具体时间、密码保护链接

### V2
- [ ] **旅行视频**：按节点顺序自动剪辑 + Ken Burns 运镜 + 地图路线动画 + 卡点配乐，竖版适配小红书/抖音
- [ ] 同行者协作：多人往同一篇游记投照片
- [ ] 人脸/风景智能选图（端侧 ML Kit，避免上传）
- [ ] 导出 PDF / 打印相册
- [ ] Live Photo、视频片段入库

## 7. 交互与视觉设计建议

**扫描结果页（魔法时刻）**：不要先给列表，先给**一张会动的地图**——路线像画笔一样逐段绘出，节点依次弹出，底部滚动出"9 月 12–19 日 · 京都·大阪 · 8 个地点 · 412 张照片"。这一屏决定用户是否留下。

**挑图页（唯一的重活）**：
- 默认已经帮用户预选好（按清晰度 + 时间分散度 + 去重），用户只需"减"不需"加"
- 大图九宫格，点击切换选中，长按放大预览
- 顶部常驻"已选 7 张"，底部"下一个节点 →"，让挑图变成有节奏的连续动作而非反复返回

**分享网页**：
- 首屏是封面大图 + 标题 + 日期，向下滚地图接管背景
- 每个节点：小标题 + 地图定位点高亮 + 照片瀑布
- 结尾放数据总结卡片，这是最容易被截图发朋友圈的部分——**要专门为"被截图"而设计**

## 8. 里程碑建议

| 阶段 | 内容 | 判定标准 |
|---|---|---|
| **W1 技术验证** | 只做一件事：在 iPhone 12 Pro Max 和 OPPO 上，各写个 Demo 把某段日期的照片 GPS+时间全部读出来打印 | 两台真机都能拿到坐标 → 项目可行 |
| W2 | 聚类算法 + 地图路线渲染（数据可先硬编码） | 路线看起来"对" |
| W3-4 | 完整 App 流程走通（本地，不上传） | 能从相册走到预览页 |
| W5 | 后端 + 上传 + 发布 | 手机上点发布，浏览器能打开链接 |
| W6 | 分享网页打磨 + 真机双平台回归 | 拿自己真实旅行发一篇出去 |

**W1 的技术验证是整个项目的生死线**，尤其是 Android 的 `ACCESS_MEDIA_LOCATION`。建议先只写这一个 Demo，别急着搭工程骨架。
