# 旅行回顾：自动精选与内容生成

---

## 1. 命名

| 概念 | 代码 | 界面（中文） | 界面（英文） |
|---|---|---|---|
| 一个停留点 | `Stop` | **站**（第 3 站 / 5 站 · 2 天） | Stop |
| 一次旅行 | `Trip` | 旅行 | Trip |
| 一段 | `Segment` | 段 | Segment |
| 侧栏入口 | — | **生成旅行回顾** | Create Trip Story |

为什么是「站」而不是「地点」或「停留点」：它天然带路线感，
和 `TOKYO ── HAKONE ── KYOTO` 是同一个心智模型；
「停留点」太技术，「地点」太平、读不出顺序。

---

## 2. 产品定位的一次收敛

> **去重 + 精选，比 GPS 更接近最终产品价值。**

地图是激发点，也是最亮的视觉资产，但用户真正说不出口却最痛的需求是：

> 「帮我从这 91 张里挑出这一天最值得看的 8 张。」

没人想在网页上翻 91 张同一个街景、同一个自拍、同一段路。
所以**自动精选是产品的核心能力，地图是它的骨架**。

同样重要的是分寸：**自动精选给的是"建议"，不是"决定"**。
一律预选好让用户确认或改，绝不悄悄替用户丢照片 ——
这和"照片库只读、不选取不等于删除"是同一套价值观。

---

## 3. 自动精选：第一版完全不用 AI

用的全是拍摄那一刻就已经存在的信号。已实现于 `tv_core/lib/src/curation.dart`。

### 3.1 信号来源

| 信号 | 怎么拿到 | 作用 |
|---|---|---|
| **清晰度** | 生成缩略图时顺便算拉普拉斯方差 | 压掉模糊、手抖 |
| **亮度** | 同上，算均值 | 压掉过曝、欠曝 |
| **感知哈希** | 同上，算 dHash（64 位） | **去重的关键** |
| **人脸数** | macOS Vision 框架，本地跑 | 有人的照片更值得放 |
| 分辨率 | EXIF | 压掉截图和网上存的图 |
| 横/竖构图 | EXIF | 横图更适合做大图 |
| 是否截图 | 文件名 + 尺寸特征 | 直接排除 |
| 是否已修图 | `IMG_E` 前缀 | 用户本来就更中意这张 |
| **是否已手动选取** | `pick` 标签 | **压倒一切**，绝不跟用户对着干 |

这些**全部在导入时一次算完**，存进 sidecar，之后精选就是纯计算，毫秒级。
生成缩略图本来就要解码一次，顺手把这几个值算出来，几乎不增加成本。

`favorite`（相册里的爱心）拿不到 —— PTP 读不到 Photos 数据库，
等做手机端时才能补上。

### 3.2 算法

```
1. 打分      组内相对排名（不同相机、不同光线的绝对值没有可比性）
2. 去重      感知哈希汉明距离 <= 8 且时间邻近 -> 归为一组
             时间间隔 < 30 秒时阈值放宽到 12（连拍就是这么产生的）
3. 排序      每组保留分最高的那张，按分数排组
4. 分散      同一个 10 分钟窗口最多选 2 张，避免全挤在同一分钟
5. 补齐      因分散限制没选够时放宽再补
6. 封面      分最高者，横构图额外加分
```

**目标张数**默认取 `sqrt(去重后的组数)`，限制在 3-10 之间。
91 张 5 个场景的一天，大约落在 8-10 张 —— 正是想要的量级。

### 3.3 为什么理由必须给用户看

`PhotoScore.breakdown` 保留每一项的贡献（清晰 +2.1 / 有人 +0.8 / 截图 -4.0）。
**自动精选如果是黑盒，用户就不会信任它，也就不敢把挑图交给它。**
界面上要能看到"为什么选了这张、为什么没选那张"，
以及"这一组里还有 17 张相似的"。

## 4. 内容生成：三个层级，现在只做 Level 0

| 层级 | 内容 | 依赖 | 什么时候做 |
|---|---|---|---|
| **Level 0** | 纯数据：`Kyoto · Oct 6–9` | 无 | **现在** |
| **Level 1** | 事实型文案：`October 7 · Kyoto` / `Photos taken around Gion and Kiyomizu-dera.` | GPS + 反查地名 + 日期 | 地名反查做完之后 |
| Level 2 | AI 叙事：`We spent three days exploring Kyoto, starting with...` | LLM | 以后 |

**现在不要碰 AI 文案。** Level 0 已经足够好看，而且永远不会说错话；
Level 1 全部来自事实，同样不会胡说。等这两层的体验打磨透了，
Level 2 才是锦上添花，而不是拿来掩盖前两层没做好。

## 5. 一次旅行自动生成四块内容

不能只输出「地图 + 照片」—— 那和普通旅行相册没有区别。

### 5.1 Trip Header

```
A Weekend in Chicago
September 3-5, 2025
3 days . 1 city . 32 photos
```

### 5.2 Route

单城市时是一条线：

```
.────.────.────.
      42.7 km
```

跨城市时列出城市序列：

```
New York
   |
Philadelphia
   |
Washington DC
```

### 5.3 Daily / Stop Stories

每一站自动生成一张**故事卡片**：一张封面大图 + 3 到 4 张配图 + 事实型标题。

```
September 3        Chicago
[ hero ]
[ 3 photos ]

September 4        Chicago -> Evanston
[ hero ]
[ 4 photos ]
```

### 5.4 Trip Summary

```
3 days
1 city
42 km traveled
32 selected photos
```

**这一张是给用户截图发朋友圈的。** 要专门为"被截图"设计：
方形或竖版、字大、留白足、不依赖上下文单独看也成立。
传播就靠它。

## 6. 三套模板（不要一开始让用户自己排版）

| 模板 | 结构 | 适合 |
|---|---|---|
| **A. Classic** | 标题 / 地图 / 时间线 / 照片 | 最稳，默认 |
| **B. Cinematic** | 巨大标题 + 满屏封面，地图淡淡浮在背景 | 单城市、照片质量高 |
| **C. Map Journey** | 地图是主角，站点横向串起来 | 长途路线，比如横穿美国 |

```
Template C:
TOKYO ───── HAKONE ───── KYOTO
  1 photo      2 photos      3 photos
```

用户只选模板，不排版。排版是我们的活。

## 7. 优先级：网页 > 长图 > 视频

这一点已经确定，不再摇摆。

| 顺序 | 形态 | 理由 |
|---|---|---|
| **1** | **分享网页** | 生成、修改、分享、手机和桌面打开、统计访问、事后更新、地图交互 —— 全都最容易 |
| 2 | 图片长图 | 微信群和朋友圈的传播形态，从网页同一份数据渲染即可 |
| 3 | 视频 | 成本最高、最难改、最难更新，放到最后 |

### 网页不是"导出结果"，而是产品本身

这句话值得单独立一节，因为它会改变很多决策：

- 网页**可以被更新**：三年后往那次旅行补几张照片，重新渲染，
  原来那个链接的内容跟着变 —— 而不是重新生成一个新链接
- 网页**有访问统计**：谁看了、看了多久，这是唯一能量化传播的形态
- 网页**是获客入口**：每一次分享都是一次曝光，页脚一行
  "用 TravelView 生成"就是全部的市场预算
- 所以**渲染器要留在产品里持续演进**，模板升级后所有老游记自动变好看，
  这正好呼应架构里"一份 manifest + 一个通用渲染前端"的设计

导出成静态包是**附加能力**（离线保存、放进硬盘），不是主形态。

## 9. 实际道路路线与"小车在跑"的动画

**定位调整**: 这不是一个 option，而是**核心产品效果**。
直线读起来是"把两个点连起来"，实际道路读起来才是"这是我的旅行路线"。
所以**默认就是道路路线**，直线只作为 fallback。

### 9.1 供应商选择：三条硬约束

| 约束 | 说明 |
|---|---|
| **结果必须能永久存** | 游记网页要十年后还能打开，路线必须写进 manifest |
| **必须能和我们自己的底图一起显示** | 底图已定为自托管 Protomaps + MapLibre |
| **不能把用户行踪送给第三方** | 和"照片从不上传"是同一类承诺 |

**Google Routes 同时踩中前两条**：它的条款既限制缓存/存储路线内容，
又要求路线结果显示在 Google 地图上，不能与非 Google 地图混用。
我们用的是 MapLibre + Protomaps —— 这一条就直接排除了它，
而且这比"缓存 30 天"更致命，因为它连"当场显示"都不允许。

**Mapbox Directions 也要谨慎**：它允许为性能做有限缓存，
但"永久存进用户的分享页并长期分发"超出了常规条款范围。
真正安全的是**基于 OSM 数据、自托管或条款允许存储的引擎**：

| 供应商 | 永久存 | 与自有底图共用 | 说明 |
|---|---|---|---|
| **OSRM（自托管）** | 可以 | 可以 | 推荐。ODbL，署名即可 |
| Valhalla / GraphHopper（自托管） | 可以 | 可以 | 同上，内存占用比 OSRM 的 CH 模式友好 |
| openrouteservice（托管） | 可以（署名） | 可以 | 免注册额度小，起步方便 |
| Mapbox Directions | 有限制 | 可以 | 长期存储条款存疑 |
| Google Routes | **不可以** | **不可以** | 两条硬约束都踩 |

**自托管的真实成本要说清楚**：OSRM 用 CH 算法预处理北美路网需要很大内存
（几十 GB 级），不是"跑个 docker 就行"。**MLD 算法**内存友好得多，
适合我们这种请求量不大的场景。起步阶段可以先用 openrouteservice 的托管额度，
量上来了再自托管。

### 9.2 用户看到的只有三个选项

界面上**不出现供应商名字** —— 用哪家是我们的实现细节：

```
路线
  ● 驾车
  ○ 步行
  ○ 直线
```

飞行段自动识别（速度 > 300 km/h），永远不贴合道路，画大圆弧虚线。
单段可以单独覆盖 —— 横穿美国这种行程里，某一段坐飞机是常事。

### 9.3 路线连接的是"站"，而且用进出口而不是中心点

一个城市里拍了 80 张照片，簇中心可能落在谁都没去过的地方。
所以 `Stop` 现在带 **entry / exit**：入口取最早那张照片的位置，
出口取最晚那张。路线连的是 `上一站的出口 -> 这一站的入口`，
贴近真实动线，也避免了在城市里连出一团毛线。

（已实现于 `route.dart`，有测试守着"中心点不等于进出口"。）

### 9.4 照片密集时可以还原真实轨迹

站与站之间如果本来就有很多带 GPS 的照片，我们手上其实已经有**真实轨迹的证据**。
OSRM 支持 map matching，可以把这些噪声点吸附到路网上。于是有两种质量：

| 情况 | 做法 | 页面上的说明 |
|---|---|---|
| 中间照片稀疏 | 路径规划推算 | 路线为推算 |
| 中间照片密集 | map matching 还原 | **根据你的照片还原** |

后者是这个产品独有的能力 —— 别人没有你的照片，做不出这条线。

### 9.5 可信度必须如实标注

`RouteSource` 三个值：`inferred`（推算）/ `reconstructed`（照片还原）/
`actual`（真实轨迹，将来接 GPX 才会有）。

页面上写「路线根据你的照片推算」，**不能写「这是你走过的路」** ——
我们并不知道用户是不是绕了风景道。这和"不选取不等于删除"是同一套价值观：
**宁可少说，不能骗人。**

### 9.6 数据结构：算一次，永久存

```
生成 Story 时:  站的进出口 -> RouteProvider -> GeoJSON LineString
                -> 抽稀 -> 存进 projects.json / manifest.json

网页打开时:      直接画存好的 polyline，不调用任何 API
```

**抽稀（Douglas-Peucker）是必须的**：横穿美国的一段路线可能上万个点，
原样存进 manifest 会让分享页 JSON 变成好几 MB，手机上打开很慢。
容差 10 米在洲际尺度上肉眼看不出差别，测试里验证了能压到十分之一以下。

manifest 里一段路线长这样：

```json
{
  "from": "tokyo", "to": "hakone",
  "mode": "driving", "source": "inferred", "provider": "osrm",
  "distanceMeters": 102340, "durationSeconds": 7200,
  "geometry": { "type": "LineString", "coordinates": [[139.65, 35.67], ...] }
}
```

（`RouteLeg` / `RouteProvider` / `DirectRouteProvider` 已实现于 `routing.dart`，
序列化和 GeoJSON 坐标顺序都有测试。`DirectRouteProvider` 永远可用、不联网，
是所有联网供应商失败时的兜底 —— **行程图任何情况下都必须画得出来**。）

### 9.7 小车动画

几何计算已经实现（`Polyline`）：累计距离、按进度插值位置、前进方向。
车头会跟着路线转弯，不是横着滑。

**跟随滚动，不自动播放**。滚到哪一天，车就开到哪一天；
走过的路线**逐渐长出来**，未走的淡着。这把 Story 的时间线和地图的时间线
绑成了一件事，比自动播放高级得多，也让用户始终掌握节奏。

放在**网页渲染器**里做，桌面端不需要。

### 9.8 修正后的实施顺序

| 步 | 内容 | 状态 |
|---|---|---|

| 2 | 原生信号（清晰度/哈希/人脸） | 已完成 |

## 10. 路线自己存：格式选型

### 10.1 一个必须先说破的误区

**把第三方的路线转存成我们自己的文本文件，并不能绕过它的授权条款。**

Google 的条款限制的是"路线内容"本身，不是文件格式。
存成 GeoJSON、GPX 还是自定义格式，都改变不了"这是 Google 的路线数据"这个事实 ——
反而"永久保存并对外分发"正是条款明确禁止的行为。

所以**自己存解决的是「依赖」和「永久性」问题，不解决「授权」问题**。
供应商仍然必须选对：用基于 OSM、允许存储的引擎（OSRM / Valhalla /
GraphHopper / openrouteservice），署名 OpenStreetMap 贡献者即可。

选对了供应商之后，自己存的思路完全正确，而且是必须的。

### 10.2 三种格式，各司其职

| 格式 | 用途 | 为什么 |
|---|---|---|
| **GeoJSON LineString** | **规范存储**：manifest 和工作进度里存这个 | 是 JSON，和其它数据同文件；MapLibre / Leaflet 直接吃；紧凑；可 grep |
| **GPX 1.1** | **导出给用户**，以及**导入真实轨迹** | Strava、Garmin、Google Earth、几乎所有户外软件都认。数据能带着走 |
| Encoded Polyline | 备选压缩方案 | 比 JSON 数组小很多，但不可读。抽稀之后 GeoJSON 已经够小，暂不需要 |

你猜得对，Strava 一类用的确实是文本格式 —— **GPX**（XML）或 TCX。
但 GPX 作为**主存储**偏啰嗦（体积约是 GeoJSON 的 3-5 倍），
所以我们**内部用 GeoJSON，对外导出 GPX**，两边都占。

### 10.3 GPX 导入是被低估的一步

用户如果有行车记录仪、运动手表、或从别的 App 导出的轨迹，
导进来就能把这段路线的可信度从 `inferred`（推算）直接升到
**`actual`（真实走过的路）**。

这是任何在线路径规划都给不了的东西，而且完全不依赖第三方。
（`Gpx.readTrackPoints` 已实现，宽松解析，能处理 lat/lon 顺序颠倒的导出文件。）

### 10.4 "关键节点"就是抽稀的结果

你说的"只存拐弯位置"，正是 Douglas-Peucker 在做的事:
它保留的恰好是改变路线形状的点（拐点），删掉直线上的冗余点。
测试里验证过"拐点必须保留" —— 拐点丢了，路线形状就错了。

### 10.5 要不要缓存渲染好的地图图片

**两种都要，但用途不同，不能互相替代。**

| | 矢量数据（GeoJSON） | 渲染好的图片（PNG） |
|---|---|---|
| 交互（缩放、点击、小车动画） | 可以 | 不行 |
| 换模板/换配色后自动更新 | 可以 | 不行，得重渲 |
| 社交预览 `og:image` | 不行 | **必须是图片** |
| 长图导出 / 微信群传播 | 不行 | **必须是图片** |
| 体积 | 几十 KB | 几百 KB |

所以：**矢量是真相，图片是产物**。分享页用矢量实时渲染（这样以后模板升级，
所有老游记的地图自动变好看）；同时在发布时生成一张 PNG 快照，
专门用于 `og:image` 和长图。

**这张 PNG 我们自己渲染**，不需要任何第三方静态地图 API ——
MapLibre 渲染到 canvas 再导出即可，底图是我们自托管的 Protomaps。
整条链路上没有一个环节依赖别人的服务器能不能活到十年后。
