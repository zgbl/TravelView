# TravelView 架构 v0.2 —— 以「开放照片库」为核心的重构

> v0.1 见 `archive-architecture-v0.1.md`。这一版按「时间目录保底 + 多视图叠加 + 零重复」重构。

---

## 1. 重新定位

原本的产品是「旅行回顾生成器」，加上备份后变成两个功能并列。这一版把它合成一件事：

**TravelView 是一个开放的照片库系统。备份是往库里写，游记是从库里读。**

一句话产品主张：

> **你的照片，是你硬盘上普通的文件夹和普通的文件。App 只是给它们加了一层可以随时丢弃、也可以随时重建的索引。**

这正是 Apple 走反了的地方——它的答案是把文件藏进 `.photoslibrary` 这个黑盒，用户永远找不到自己的照片；而纯文件夹的传统方式又丢掉了多维度组织能力。**两者不是二选一：文件是真相，索引是视图。**

---

## 2. 五条架构原则

这五条是后面所有设计的推导起点，写代码时如果和某条冲突，改设计不改原则。

**原则 1｜文件是唯一真相（Files are the source of truth）**
照片以原始字节、原始文件名、普通文件的形式存在按时间组织的目录里。不打包、不加密、不改名、不转码。断网、卸载 App、公司倒闭、十年后——用 Finder 双击就能打开。

**原则 2｜一张照片只存一份字节**
无论它属于几次旅行、几个人物、几个相册。任何"分类"都不产生第二份副本。

**原则 3｜索引可以完全重建**
删掉数据库，从文件树 + sidecar 就能一字不差地重建出全部组织信息。这既是防数据损坏，也是**反厂商锁定的承诺**——用户任何时候可以不要你，而这恰恰是他们敢用你的原因。

**原则 4｜用户可以随便动文件，库能自愈**
用户在 Finder 里改名、移动、重新分类，App 靠**内容哈希**重新认领，不报错、不重复导入、不丢元数据。Apple 的库你一动就烂，这是它最招人恨的地方，也是最大的可攻击点。

**原则 5｜视图层不依赖任何文件系统特性**
理由见下一节。

---

## 3. 索引层：用 DB + JSON 组织，而不是用目录组织

### 3.1 先定一件事：谁是真相

DB 和 JSON 都要有，但必须明确主从，否则两边不一致时无从判断谁对。

**决策：sidecar JSON 是真相，SQLite 是可丢弃的派生缓存。**

| | 角色 | 理由 |
|---|---|---|
| `.tvmeta.json`（每个日期目录一个） | **真相** | 跟着照片走，人可读，格式开放，拷贝文件夹时元数据一起走 |
| `catalog.sqlite` | 派生缓存 | 查询快、支持任意维度联表；损坏或版本升级直接删掉重建 |
| `catalog.jsonl` | 全库文本镜像 | 可 grep、可进 git、可 diff；也是 sidecar 散落时的汇总快照 |

这个主从关系直接兑现了原则 3：`rebuild` 就是"遍历文件树 + 读所有 sidecar → 重建 SQLite"。SQLite 里**永远不允许存在唯一一份的信息**——任何写入 catalog 的内容，必须同时落进对应的 sidecar。这条是硬约束，写代码时要有测试守着。

10 万张照片的规模下，JSON 全量解析约几秒，SQLite 查询是毫秒级——所以查询走 SQLite，可信度靠 JSON。两者各司其职，不矛盾。

### 3.2 组织能力全部落在 tag 表上

```sql
-- 某次旅行的照片，按时间
SELECT p.* FROM photo p JOIN tag t ON t.photo_id = p.id
WHERE t.kind='trip' AND t.value='kyoto-2025' ORDER BY p.taken_at;

-- 同时属于「京都」和「有妈妈出镜」的照片
SELECT photo_id FROM tag WHERE kind='place' AND value='京都'
INTERSECT
SELECT photo_id FROM tag WHERE kind='person' AND value='mom';

-- 2025 年拍了但一次都没被用进任何游记的照片
SELECT p.id FROM photo p WHERE strftime('%Y', p.taken_at)='2025'
  AND NOT EXISTS (SELECT 1 FROM tag WHERE photo_id=p.id AND kind='trip');
```

一张照片可以同时挂任意多个 tag，字节永远只有一份。加一个新维度（天气、相机型号、"值得打印的"）不需要改架构、不产生任何文件副本——这正是目录结构做不到、而 DB 天生就能做的事。

### 3.3 「导出成文件夹」是一个动作，不是一种存储方式

用户偶尔确实需要真实的文件夹（发给家人、导进 Lightroom、刻盘）。这时候执行一次 **export**，而不是让库常年维护一堆并行目录：

```
tv export --trip kyoto-2025 --as html        # 默认
tv export --person mom --year 2025 --as copy --to /Volumes/给妈妈的U盘
```

`--as` 的五种形态，按文件系统能力自动降级：

| 形态 | 占空间 | exFAT | 说明 |
|---|---|---|---|
| **html**（默认） | 几乎为零 | **可用** | 单个 `index.html`，相对路径链到真实文件，双击浏览 |
| **shortcut** | 几乎为零 | **可用** | 生成 `.webloc`(macOS) / `.url`(Windows)，本质是普通文本文件，所以不受文件系统限制；双击打开原图 |
| symlink | 零 | 不可用 | APFS / ext4 / NTFS 上才生成 |
| hardlink | 零 | 不可用 | 同卷内才可用 |
| copy | 全量 | 可用 | 真拷贝，用于交付给别人 |

`.webloc` / `.url` 这一档值得单独说：它们只是内容为一行路径的**普通文本文件**，因此在 exFAT、FAT32、任何介质上都成立，等于一个跨平台可用的"穷人版软链接"。缺点是平台专属（macOS 的 `.webloc` 在 Windows 上没用），所以两种一起生成，或者干脆用 html。

### 3.4 更远的一步：让视图在 Finder 里"就是文件夹"

如果要做到用户在 Finder 里直接看到 `按旅行/京都 2025/`，且不占空间，正统做法是 macOS 的 **File Provider Extension**（Dropbox、OneDrive 现在用的机制），Windows 侧对应 Cloud Files API。它能把数据库里的视图呈现成真实目录，零重复。

但这是一大块专门工作，且必须原生实现（Flutter/Tauri 都覆盖不到）。**建议 v1 不做**，先用 html + shortcut 顶住。等产品被验证之后，这会是让人惊叹的那一步。

（顺带排除一个选项：macFUSE 也能做虚拟目录，但它依赖内核扩展，在 Apple Silicon 上要用户降低安全设置，装机门槛太高，不适合面向普通用户的产品。）

## 4. 磁盘布局

```
TravelView/                            备份目的地根目录
  photos/                              原件唯一存放处，按拍摄时间
    2025/
      2025-03-14/
        2025-03-14 09-21-05 IMG_1180.HEIC
        2025-03-14 09-21-05 IMG_1180.MOV      Live Photo 的动态部分，同名配对
      2025-09-12/
        2025-09-12 14-30-22 IMG_1234.HEIC
        .tvmeta.json                          该目录的 sidecar
  views/                               视图层，可随时删除重建，不含照片字节
    by-trip/
      2025-09-12 京都·大阪 8天/
        index.html                            该次旅行的游记（离线可看）
        trip.json
        photos/                               软链接（exFAT 上此目录不生成）
    by-place/
    by-person/
    by-album/                                 还原手机里的相册结构
  catalog/
    catalog.sqlite                            索引，可从上面两层完全重建
    catalog.jsonl                             纯文本镜像，人可读、可 grep、可版本控制
  index.html                                  总入口，双击即用
  TRAVELVIEW.md                                说明这个目录怎么组织的，给十年后的你自己看
```

几个刻意的选择：

- **文件名带可读时间戳**：在任何文件管理器里按名字排序就是按时间排序，不依赖 mtime（复制会丢）。
- **sidecar 跟着照片走**：`.tvmeta.json` 放在照片同级目录，用户拷走某个文件夹，元数据一起走。
- **`catalog.jsonl` 是纯文本**：SQLite 损坏时的第二道保险，也让技术用户能直接 grep。这个细节会让懂行的人立刻信任你。
- **`TRAVELVIEW.md`**：一份写给未来的说明书。成本几乎为零，传达的信号极强。

## 5. 照片身份：内容寻址

一切自愈能力的基础。

```
photo_id = BLAKE3(原始文件字节)[:16]        // 内容哈希，与文件名/路径/设备无关
```

它带来四件事：

1. **跨设备去重**：你 iPhone 和 OPPO 里的同一张照片，是同一个 id，只存一份。
2. **重复导入无副作用**：同一张照片扫十次也只有一份。
3. **用户随便动文件**：改名、移动后，重新扫描时靠哈希认出"这就是那张"，把元数据接回去。
4. **备份校验**：目标端重算哈希即可确认完整性。

工程细节：全量哈希大文件慢，先用 `(文件大小 + 前 64KB + 后 64KB)` 做快速指纹筛掉绝大多数，命中才算全量哈希。

**一个必须处理的例外**：iOS 编辑过的照片有"原片"和"编辑后"两份字节，是两个 id。用 `edit_of` 字段把它们关联起来，UI 上折叠成一张。

## 6. 数据模型（catalog）

```
photo        id(hash), taken_at, tz, lat, lon, w, h, mime, bytes,
             orig_filename, device, live_video_id, edit_of, is_screenshot
location     photo_id, path            一张照片可在多个目的地各有一份路径
trip         id, title, start, end, cover_photo_id, slug
trip_node    id, trip_id, seq, day, name, lat, lon, arrive_at, leave_at
tag          photo_id, kind(trip_node|album|person|place|keyword), value
             ← 所有"分类"都落在这张表，多维度共存，零文件重复
backup_job   destination_id, photo_id, state, verified_at, hash_checked
destination  id, name, root_path, fs_type, supports_symlink, last_seen_at
```

**核心就是 `tag` 表**：旅行、相册、人物、地点全都是同一种东西——贴在照片上的标签。视图 = 对 tag 表的一次查询 + 一次渲染。加一个新维度不需要改架构，也不产生任何文件副本。

## 6.5 桌面端直连手机读照片（USB）

### 6.5.1 结论先行

| 通道 | 可行性 | 能拿到什么 |
|---|---|---|
| **Android + USB (MTP)** | **完全可行** | 全部照片原件 + 完整 EXIF/GPS。手机上不需要装任何东西 |
| **iPhone + USB (PTP / AFC)** | **可行，有边界** | DCIM 里的原件 + 完整 EXIF/GPS。相册结构拿不到；被 iCloud 抽走的原件拿不到 |
| 蓝牙 | **不可行** | 见下 |
| Wi-Fi（手机推） | 可行 | 全部，但需要装 App |

### 6.5.2 Android：MTP，没有悬念

Android 通过 MTP 把整个媒体库暴露给电脑，桌面端用 **libmtp / libusb** 枚举和拉取，
拿到的是原始文件，EXIF 和 GPS 一个字节不少。手机端不需要装 App，也不需要开发者模式。

唯一的用户操作是：插线后在手机上把 USB 模式从"仅充电"切到"传输文件"。这个必须在 UI 上引导。

### 6.5.3 iPhone：PTP / AFC，能拿到的比多数人以为的多

iPhone 插上电脑时会把自己暴露成一台**相机**（PTP 协议）。macOS 自带的「图像捕捉」
和「照片」App 导入走的就是这条路，第三方 App 可以用 **ImageCaptureCore** 框架做同样的事。
另一条路是开源的 **libimobiledevice**（AFC 服务），能直接读 `/DCIM`，跨平台。

**能拿到**：相机拍的照片和视频原件、截屏、Live Photo 的 HEIC + MOV 配对文件，
以及**完整的 EXIF，含 GPS**。这恰好就是做行程还原需要的全部东西。

**拿不到的三样，必须认**：

1. **被 iCloud「优化存储」抽走的原件**。设备上只有缩略图时，PTP 无能为力——
   它只能看到文件系统里真实存在的东西。**只有装在手机上的 App 才能通过 PhotoKit
   把原图从 iCloud 拉回来。** 这是手机端不可替代的唯一硬理由。
2. **相册结构、收藏、标题**。这些只存在 Photos 数据库里，DCIM 里没有。
3. **编辑后的版本**。DCIM 里通常是原片。

### 6.5.4 蓝牙：不用考虑

两个独立的否决理由，任何一个都足够：

- **带宽**。蓝牙实际吞吐约 1-2 Mbps。一次旅行 300 张、每张 3 MB，约 900 MB，
  理论最快也要**一个多小时**，实际会更久。用户不会等。
- **iOS 根本没有这个 API**。Apple 不向第三方开放蓝牙文件传输，只有 AirDrop，
  而 AirDrop 无法被程序调用。

无线的正确答案是 **Wi-Fi 同网段推送**，不是蓝牙。

### 6.5.5 这对产品意味着什么

USB 直读成立，意味着**桌面端可以是一个不需要手机 App 的完整产品**：

```
插上手机 -> 桌面端读出照片和 GPS -> 建库 -> 聚类出行程 -> 挑图 -> 生成游记和备份
```

全程没有 App Store 审核、没有 iOS 后台限制、没有本地网络权限弹窗、
没有"用户装不装得动 App"的转化漏斗。**这是一条比手机端短得多的路。**

手机端不会因此消失，它的不可替代价值收敛成三条，而且都很实：

1. **iCloud 优化存储的用户**，只有 App 能把原图拉回来（很可能是多数 iPhone 用户）
2. **相册结构、收藏、人物**，只有 PhotoKit 能读到
3. **不插线的日常增量备份**，Wi-Fi 推送

## 7. 组件

**手机端（Flutter）** —— 库的写入源
相册只读扫描、EXIF/GPS 提取、内容哈希、行程聚类、挑图 UI、推送到目的地。

**桌面端（Tauri）** —— 库的管理者
Bonjour 广播、接收推送、落盘、生成视图与 `index.html`、校验、多目的地管理、全库浏览。你已有 Tauri 经验，这块是舒适区。

**云端（Go，可选）** —— 只做分享
仅在用户点"发布网页"时参与，存的是压缩过、剥了 EXIF 的分享副本。**备份链路完全不经过服务器**，纯局域网，边际成本为零。

**关键**：手机和桌面端之间只有局域网。这既是隐私卖点也是成本结构——用户增长不带来服务器账单。

## 8. 四个核心流程

**首次导入**：扫描元数据 → 快速指纹去重 → 按时间落盘 → 写 sidecar → 建 catalog → 生成视图。
最旧优先，随时可中断续传。

**增量**：只查上次扫描点之后的资产，几秒完成。

**重建（`rebuild`）**：删掉 catalog，遍历文件树 + 读 sidecar，全量重建。
**这个命令必须从第一天就能跑通并写进测试**——它是原则 3 的可执行证明。如果它不能跑，整个"开放"的承诺就是空话。

**校验（`verify`）**：目标端逐个重算哈希比对，输出报告。没有校验的备份是自我安慰。

---

## 9. 游记功能在新架构里的位置

它变成了**视图层的一个渲染器**：查 `tag` 表拿到某次旅行的节点和照片 → 渲染成 `index.html`。

同一个渲染器输出两份：一份写进硬盘（离线、永久、无依赖），一份上传发布（在线分享）。**同一份代码，两个出口。**

这也意味着：游记不再是"生成一次就固化"的产物。用户三年后往那次旅行里补几张照片，重新渲染一下，网页和硬盘上的那份一起更新。

## 10. 实施顺序

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| **S0** | 相册读取技术验证（两台真机读出 GPS+时间） | OPPO 上能拿到经纬度 |
| **S1** | 库的核心：哈希、落盘、sidecar、catalog、`rebuild`、`verify` | 删库能完整重建，校验全绿 |
| **S2** | Android 备份全链路（直写 OTG 硬盘，不需要桌面端） | 真机备份一次旅行并校验通过 |
| **S3** | Tauri 桌面端 + Bonjour 推送 + `index.html` 生成 | 插硬盘双击能浏览 |
| **S4** | 行程聚类 + 挑图 UI + 游记渲染 | 生成第一篇游记 |
| **S5** | iOS 备份（iCloud 下载、Live Photo、前台限制） | iPhone 跑通 |
| **S6** | 发布分享站 | 链接能发出去 |

顺序变了：**先做库，再做游记**。因为库是地基，游记是地基上的第一个应用。反过来做会导致游记的数据模型绑死在临时结构上，S1 时全部返工。

代价是"魔法时刻"来得晚一些。可以在 S2 就用命令行输出一个粗糙的行程摘要，让自己先看到效果。

## 11. 关于「五年后卖给 Apple」

说点实在的。Apple 收购的从来不是功能，是它自己做不了或来不及做的东西。而这个架构里真正稀缺的，恰恰不是技术——哈希去重、目录组织、SQLite 索引，都不难——**是那个"你随时可以不要我"的承诺**。Apple 的商业模式建立在 iCloud 订阅上，它在结构上就说不出这句话，这是你唯一的、也是真实的护城河。

所以有一件事要想清楚：这个承诺一旦兑现（用户随时能带着完整的开放格式照片库离开），你就很难再靠锁定收费；而它一旦打破，你和 iCloud 就没有区别了。这不是坏消息，只是意味着收入必须来自"持续提供价值"而不是"持续扣着数据"——一次性买断、桌面端付费、家庭共享，都比订阅更契合。

至于并购本身，它不是能规划的路径，把它当作副产品而不是目标会让决策清醒得多。真正值得盯住的指标只有一个：**有多少人在用了半年之后，还在每个月插一次硬盘。**
